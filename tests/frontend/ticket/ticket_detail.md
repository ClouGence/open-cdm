# 工单详情

## Purpose

验证工单列表检索入口、工单创建校验和工单详情完整生命周期，重点防止筛选项重复、资源标识不清、规则校验结果侵占编辑器、状态与处理人错位、步骤时间、分析结果和 SQL 预览错位，以及自动刷新、步骤切换和窄屏布局回归。

## Scope

- 页面：工单列表、工单创建、工单详情。
- 路由：`/#/ticket`、`/#/ticket_create`、`/#/ticket/:id`。
- 接口：工单列表、工单基础信息、数据库工单详情、SQL 分段预览、审批、执行确认、关闭工单以及自动执行任务相关接口。
- 状态：初始化、分析、等待审批、等待确认、待执行、执行中、完成、拒绝、失败、关闭、取消。
- 不覆盖：审批规则配置、SQL 解析器正确性、执行引擎性能和第三方审批系统内部页面。

## Preconditions

- 本地 `DmAloneLauncher` 已启动，访问地址为 `http://127.0.0.1:8222/`。
- @Browser 已登录具备工单查看权限的账号；审批、确认、执行等场景使用具备对应按钮权限的账号。
- 准备一个包含完整生命周期数据的数据库变更工单，以及一个处于非终态、可安全推进的测试工单。
- 所有写入和执行场景仅允许使用本地测试数据库，SQL 不得修改生产数据。

## Test Data

- 完整工单：包含创建、分析、审批、确认、执行步骤；分析至少包含行为分析和安全规则结果。
- 自动执行工单：分别准备一条 `DM_QUERY` 和一条 `DM_CHANGE` 工单，两者均通过自动执行生成任务和调度日志。
- 进行中工单：使用 `SELECT 1;` 等无副作用 SQL，工单名称或描述带唯一标识 `codex_ticket_<时间戳>`。
- 创建工单数据源：至少准备两个环境，每个环境至少包含一个当前账号有权申请的数据源实例，并记录实例名称与所属环境。
- 边界工单：描述为空、超长描述、无附件名的行内 SQL、单行 SQL、多行 SQL、含中英文与特殊字符的 SQL。
- 异常数据通过浏览器开发者工具的网络条件或可控测试服务返回构造，不直接修改生产或共享环境数据。
- 清理时关闭未完成工单，并删除测试发布流或测试数据源中仅为本流程创建的数据。

- 时间范围：选择开始和结束日期及时间后查询，检查结果位于范围内；清空范围后再次查询，检查结果恢复。窄屏下日期与时间纵向排列，选择面板和确认按钮完整可见。

预期结果：检索栏保留时间范围、查询类型、查询内容和查询按钮；查询类型默认选中“工单号”，输入框默认提示“请输入工单号查询”，不显示“等待分析 /

### TD-PARSER-01 MySQL 索引访问方式审核

- 风险/目的：P0，防止合法的 `USING BTREE` 索引语句被安全审核判定为不支持。
- 初始路由与状态：进入 `/#/ticket_create`，选择隔离 MySQL 实例与测试库。
- 测试数据：测试库包含 `device_feeding_record_snapshot(feeding_record_id)`、`device_gateway_version(delete_flag,status,create_time,id)` 和 `device_gateway(serial_number)` 三张表。
- 准备方法：创建独立测试环境和安全规范，启用规范及至少一条适用于 MySQL 的查询规则，并绑定测试环境；确认实例属于该环境。确认至少一条启用规则可命中测试 SQL，不能把规范禁用或规则列表为空时的直接提交当作通过。连接账号只授予测试库的查询权限，不审批或执行测试工单。
- 操作步骤：填写唯一标题、描述和以下 SQL，点击“校验并提交”；进入工单详情的“分析”步骤，核对行为分析与安全规则结果。

```sql
ALTER TABLE `codex_issue385`.`device_feeding_record_snapshot`
ADD INDEX `idx_record_id` (`feeding_record_id`) USING BTREE;

ALTER TABLE `codex_issue385`.`device_gateway_version`
ADD INDEX `idx_status_time` (`delete_flag`,`status`,`create_time`,`id`) USING BTREE;

ALTER TABLE `codex_issue385`.`device_gateway`
ADD INDEX `idx_serial_number` (`serial_number`) USING BTREE;
```

- 预期结果：不出现 `IndexTypeContext: USING BTREE` 分析失败；工单创建成功并停留等待审批，行为分析显示 3 条 SQL、3 个索引 CREATE 和 3 个表 ALTER，安全规则分析完成且无解析阻断。若命中测试规范中其他业务规则，按对应规则独立判断，不应出现解析不支持。更换测试库名时同步替换 SQL 中的库名。
- 恢复/清理：关闭工单，不审批或执行；确认测试索引未实际创建。删除仅为此流程创建的实例、环境和规范，不修改共享环境配置。

  1px
  外框，摘要行和表格组件不重复绘制外框，表格内部行列分隔保留；页面没有全局“展开详情/收起详情”按钮；箭头位于每个分析项最前面，只控制所属分析项；展开与收起时箭头旋转、容器高度、内容透明度和轻微位移连续过渡，没有瞬间跳变；明细在该分析项容器内部、摘要行正下方展示；切换到另一项后原容器收起、目标容器展开，展开和收起不导致其他摘要行错位；系统开启“减少动态效果”时不播放明显过渡。

- 准备方法：确认实例指向本流程创建的临时数据库，记录实际产品、驱动版本和连接信息。PostgreSQL 可在自己的临时容器内使用 `pg_stat_activity` 定位目标数据库、账号及慢查询；只对已确认的目标连接执行 `pg_terminate_backend`。该替代场景验证共享执行流程，不能代替 SQL Server JDBC 读取超时验证。
- 操作步骤：提交、审批成功对照工单，立即执行并打开事务模式；确认完成后刷新。另建慢查询工单，同样启用事务立即执行，等待任务显示执行中，再终止目标数据库连接；观察自动刷新，查看任务日志，整页刷新后再次核对状态、执行次数及重试和终止按钮。
- 预期结果：成功对照的执行步骤和任务均完成，执行次数为 1；断连工单的执行步骤和任务均失败，执行次数为 1，任务日志保留原始数据库错误，重试和终止入口可用，刷新后不会回到执行中或重复执行。结束时释放会话，不再依赖恢复 auto-commit 才能上报状态。
- 配套故障注入：构造原始 `Read timed out` 与回滚抛出连接已关闭异常的组合，确认仍上报一次 `JOB_FAILED`、保留 `TASK_FAILED` 的原始错误并关闭会话；正常事务提交、可正常回滚的暂停以及关闭异常分别保持完成、暂停和已上报失败状态。只在临时探针中构造依赖故障，不改写工单状态。
- 恢复/清理：通过“终止”关闭本流程的失败工单，保留正常完成工单与必要证据；删除临时数据源并移除本流程创建的数据库容器，不清理共享数据库或工单记录。

### TD-FAILURE-04 事务与非事务失败后的重试

- 风险/目的：P0，验证断连失败后可新建连接重试成功，并防止已提交 SQL 重复执行或事务回滚后的 SQL 被遗漏。
- 初始路由与状态：从工单列表新建两张 SQL 工单；使用具备审批、执行和重试权限的账号，以及本流程创建的独立 PostgreSQL 容器。
- 测试数据与准备：在临时数据库的 `public` schema 执行以下 SQL；每次使用全新容器，避免依赖历史工单或固定业务 ID。

```sql
CREATE TABLE public.codex351_retry_marks(mode TEXT, step TEXT);
CREATE TABLE public.codex351_retry_gate(mode TEXT PRIMARY KEY, enabled BOOLEAN);
INSERT INTO public.codex351_retry_gate VALUES ('transaction', TRUE), ('plain', TRUE);
CREATE FUNCTION public.codex351_retry_delay(test_mode TEXT) RETURNS INTEGER LANGUAGE plpgsql AS $$
BEGIN
    IF (SELECT enabled FROM public.codex351_retry_gate WHERE mode = test_mode) THEN
        PERFORM pg_sleep(120);
    END IF;
    RETURN 1;
END;
$$;
```

- 工单 SQL：每张工单包含以下三条语句，非事务工单将全部 `'transaction'` 替换为 `'plain'`；标题包含模式及唯一后缀。

```sql
INSERT INTO public.codex351_retry_marks VALUES ('transaction', 'before');
SELECT public.codex351_retry_delay('transaction');
INSERT INTO public.codex351_retry_marks VALUES ('transaction', 'after');
```

- 操作步骤：校验、提交并审批工单；事务工单打开事务模式，非事务工单关闭事务模式，分别立即执行。等待第二条 SQL 执行中，在自己的临时容器用 `pg_stat_activity` 按目标数据库、账号和完整慢查询定位连接，仅终止该连接。等待失败，查看第二条任务日志，并通过独立连接查询标记表。将对应模式的 gate 更新为 `enabled=FALSE`，解除慢查询条件；在页面点击“重试”，核对确认弹窗后提交，等待执行步骤及三条任务完成。查询标记表、检查会话释放，整页刷新复核状态与次数。
- 事务预期：失败时三条任务依次为回滚、失败、等待，执行次数 `1 / 1 / 0`，标记表该模式无记录；重试成功后三条任务完成，次数 `2 / 2 / 1`，`before`、`after` 各一行。
- 非事务预期：失败时三条任务依次为完成、失败、等待，次数 `1 / 1 / 0`，只有一条 `before`；重试成功后次数 `1 / 2 / 1`，`before`、`after` 各一行，第一条 SQL 不重复执行。
- 两种模式共同预期：失败日志保留数据库断连原始错误，重试成功后历史错误仍可查看；刷新后完成状态与次数保持一致，Worker 重试使用新会话，临时数据库无遗留执行连接。此场景验证共享执行流程，不等同于 SQL Server JDBC 读取超时验证。
- 恢复/清理：失败且未完成重试的工单通过“终止”关闭；完成工单保留正常业务记录。删除临时数据源，移除本流程创建的数据库容器，恢复后端原运行状态，不清理共享数据。


### TD-FAILURE-05 自动执行打包失败日志

- 风险/目的：P0，防止 Console 打包失败只写服务器日志，调度日志和工单执行状态丢失实际失败原因。
- 初始路由与状态：从工单列表创建查询工单，账号具备提交、审批、执行、重试及终止权限；后端已加载本次 Console 构建。
- 测试数据与准备：使用本次创建、仅绑定回环端口的临时 PostgreSQL 容器和独立数据库，注册唯一命名数据源。优先用 `SELECT * FROM public.<本次唯一且不存在的表名>;` 触发元数据分析失败，并核对实际报错在 Console 打包阶段。若当前配置直接派发给 Worker，则使用本次失败工单作业，在已核对的 `app.data/temporary/exec/<jobId>.tasks.zip.tmp` 路径创建含唯一测试标记文件的目录；路径必须属于本次工单且原先不存在。该目录使打包的文件准备步骤失败，不修改工单数据库状态、业务 SQL或共享目录。
- 操作步骤：校验提交、审批通过，选择立即自动执行；若缺失表错误发生在 Worker，则按上述方式注入文件故障后点击重试；等待 Console 打包失败后打开“调度日志”。整页刷新并重新打开日志；保持表不存在，点击重试并再次查看日志。随后移除本次测试标记及其目录，仅在临时库中创建对应表、插入一条标记行，点击重试并观察结束状态，再整页刷新。
- 预期结果：打包失败的作业和执行步骤显示失败，任务保持待执行，执行次数不因打包失败增加，没有再次派发到 Worker；调度日志有 ERROR 记录，包含准备执行语句失败及实际根因（缺失表或文件准备错误），语言沿用作业创建时的语言。刷新后日志仍存在，每次失败重试增加一条对应错误日志；消除故障后重试成功，任务执行次数只因成功执行增加 1，原失败日志保留，不重复执行查询。
- 状态复核：工单 `statusMessage` 应保存实际错误信息；执行准备活动已进入运行状态时，其 `errorMessage` 应保存同一信息；通过隔离元数据库或已授权的服务端探针复核持久化状态，页面 `EXEC_FAIL` 概览不展示 `statusMessage` 的现有行为不作为该字段未保存的证据，不为本场景修改页面。
- 配套故障注入：以原始实现为对照验证日志缺失；新实现覆盖中英文、默认语言、重复调度未取得执行权、重复失败重试、已终止/删除作业，以及日志或状态保存异常时的事务回滚。不改写真实工单状态来制造分支。
- 恢复/清理：通过终止关闭本次仍失败的工单，保留已完成工单及必要证据；删除本次临时数据源、移除临时容器和仅为本流程生成的凭据文件，保持用户原有服务与业务库不变。

### TD-LIFECYCLE-01 页面生命周期

- 风险/目的：P1，确认刷新、离开与重新进入行为稳定。
- 初始路由与状态：非终态工单详情。
- 测试数据：进行中工单。
- 准备方法：打开工单详情。
- 操作步骤：刷新页面；切换到其他标签页超过一个轮询周期再返回；通过侧边栏离开后使用浏览器后退重新进入。另用隔离测试环境新建至少三个团队环节的安全 `SELECT 1;` 工单，每环节由测试账号一票通过；先手动展开后续团队，再在当前团队审批通过；重新展开已完成团队和后续团队后，通过第二团队，逐次核对展开状态。不得推进用户正在手动测试的工单。
- 预期结果：首次进入或整页刷新时，进行中工单选中当前步骤，已完成工单选中最后一步；当前步骤为内置审批时，当前正在审批的团队明细默认展开，直接显示逐人结果、时间、意见及当前用户可用的审批操作，其他已完成和未开始团队默认收起，仍可手动展开查看。每次审批进入下一团队时，自动展开新的当前团队，其他团队自动收起，包括之前手动展开的已完成或未开始团队；同一团队内投票尚未达到通过人数、手动收起当前团队或展开其他团队后，同一环节的自动刷新不覆盖手动展开状态。SQL 与权限工单使用一致规则，开发服务及后端打包页面均须复测。页面内刷新保留仍然有效的手动步骤选择；页面不可见时不进行无意义刷新；返回后恢复更新；离开页面后计时器和
  SQL 请求不再继续；重新进入不出现重复轮询。
- 恢复/清理：通过正常关闭入口关闭本场景新建的未完成测试工单，保留审批审计，不执行 SQL；返回工单列表。

### TD-PERMISSION-01 权限与登录失效

### TD-STATE-01 状态一致性

- 风险/目的：P0，确认概览、进度、步骤详情和任务执行状态使用同一服务端事实。
- 初始路由与状态：进行中工单详情。
- 测试数据：可推进至完成或失败的测试工单。
- 准备方法：按正常流程推进工单。
- 操作步骤：在分析、审批、确认、执行各阶段观察概览状态和进度；完成后等待自动刷新并手动刷新复核。
- 预期结果：同一时刻各区域状态一致；未开始步骤保持未开始且处理人显示 `-`；完成时间只在终态出现；进入终态后自动轮询停止；手动刷新结果与服务端一致。

### TD-STATE-02 空闲工单与人工操作后的推进

- 风险/目的：P0，防止等待人工审批或失败处理的工单持续写库，以及停止空转后无法恢复正常推进。
- 初始路由与状态：从工单列表分别进入内部审批的待审批工单、待确认工单和执行失败工单。
- 测试数据：使用隔离数据库中的 `DM_QUERY` 和 `DM_CHANGE` 工单；失败工单由可控的测试执行错误产生，后续能安全重试。
- 准备方法：通过正常创建与执行流程构造工单并记录其 ID；失败原因必须可在测试环境消除，不直接改写工单状态。
- 操作步骤：在详情页停留至少两个低频检查周期（当前每轮完成后间隔 60
  秒），期间仅查看和刷新；随后审批通过、完成执行确认；对失败工单消除测试故障并点击重试。每次状态变化后重新进入详情核对持久化结果。
- 预期结果：等待期间状态、步骤内容与处理人保持稳定；审批和确认操作后正常推进，重试后显示新的执行进度并最终完成或给出实际失败原因；刷新不会将新状态恢复为等待或旧失败。后台正常工单按分页扫描推进，每轮完成后间隔
  5 秒，大批量或队列繁忙时不以固定 5 秒作为完成时限。
- 数据库配套检查：在隔离元数据库中同时观测目标工单的修改时间、对应流程及 binlog；稳定空闲期间没有这些工单的周期性写入。页面状态不变本身不能证明后台零写入。
- 恢复/清理：按现有业务入口关闭或完成测试工单，恢复用于制造失败的测试条件。

### TD-REPEAT-02 确认与处理人刷新竞争

- 风险/目的：P0，防止确认阶段的旧轮询覆盖用户实际确认信息。
- 初始路由与状态：两个 @Browser 标签页打开同一张待确认测试工单。
- 测试数据：有执行权限的账号及可安全执行的工单，确认时填写可辨认的测试备注。
- 准备方法：从列表打开详情并在第二个标签页重新进入相同工单，确认两个页面均处于待确认阶段。
- 操作步骤：一个页面保持刷新，另一个页面完成确认；等待执行状态更新后，分别刷新两个页面，查看确认步骤中的处理人和备注。
- 预期结果：确认完成后两个页面显示一致的实际处理人和备注，候选执行人名单不会覆盖已完成确认的信息；重复确认被当前状态校验拒绝，不生成重复执行作业。
- 恢复/清理：关闭第二个标签页并完成或关闭测试工单。

### TD-STATE-03 Doris 非事务工单终态

- 风险/目的：P0，防止 SQL 已写入 Doris 后，非事务工单在收尾阶段调用不支持的事务接口，导致任务一直显示执行中。
- 初始路由与状态：从工单列表创建 SQL 工单，使用具备审批和执行权限的测试账号。
- 测试数据：本地 Doris 隔离测试库、带唯一前缀的测试表，以及带不同唯一标识的两条 INSERT 工单；成功工单插入一行，失败工单引用测试表中不存在的列。
- 准备方法：按本机测试数据库文档启动已有 Doris FE、BE，保留原数据；确认 SQL 端口可连接、BE 存活，并为单节点测试表配置一份副本。核对 CloudDM 实例确实指向该测试服务，记录实际 Doris 版本与测试表初始行数。
- 隔离替代环境：没有已有测试实例时，可使用 [官方 all-in-one 镜像](https://doris.apache.org/community/developer-guide/all-in-one-image/) 创建无挂载卷的临时容器，SQL 端口仅绑定 `127.0.0.1`。等待容器健康，核对 `SHOW BACKENDS` 中 BE 存活后创建唯一命名测试库；测试表使用 `DUPLICATE KEY`，避免唯一键覆盖掩盖重复执行。通过 `SHOW FRONTENDS` / `SHOW BACKENDS` 的 `Version` 记录实际 Doris 版本，不把 MySQL 协议的 `VERSION()` 字符串作为产品版本，也不把其他版本的通过结果写成已验证 issue 报告版本。
- 操作步骤：通过工单创建入口选择 Doris 实例、catalog 和测试库，SQL 使用完整库表名；校验并提交、审批通过，在执行弹窗选择立即执行并关闭事务模式。观察任务结束状态和执行次数，查看任务日志并查询测试行；刷新页面、从列表重新进入，确认状态保持一致。对不存在列的 INSERT 重复提交和执行，检查失败状态和数据库原始错误。
- 预期结果：成功工单的执行步骤和任务均进入完成状态，执行次数为 1，测试行只新增一行，刷新不会重复执行；失败工单进入失败状态，日志包含原始数据库错误且没有新增测试行。两者均不持续停留在执行中，后端收尾日志不出现 `setAutoCommit: Doris Unsupported.`。
- 对照验证：在支持事务的本地测试数据源上分别执行事务成功与失败工单，确认提交与回滚路径正常；需要验证暂停时，使用可控慢查询暂停工单，核对暂停状态、事务回滚与会话释放，不对成功 INSERT 工单盲目重试。
- 日志复核：按本次启动时间及工单作业范围检查 Worker 收尾日志，确认成功、失败均已上报终态且没有调用 Doris 不支持的 auto-commit 恢复；页面刷新和从列表重新进入后执行次数仍为 1，独立数据库连接复核成功行仅一条、失败 SQL 没有新增行。
- 恢复/清理：关闭仅为本流程创建的未完成测试工单，保留必要复现证据；只清理本流程的隔离测试数据。若使用本流程自建的临时容器，删除临时数据源并移除该容器，恢复后端原运行状态；不删除共享库表或数据库容器数据卷。

## Skip Conditions

- 没有审批或执行权限账号时，可执行只读布局、步骤切换和 SQL 内容场景；权限按钮与真实审批/执行操作标记为 SKIP，并记录未覆盖权限路径。
- 没有可安全执行的隔离数据库时，审批、确认和执行写入场景必须 SKIP；可使用已有终态工单验证只读展示，但不能替代状态推进验证。
- 无法稳定构造 400/403/500 或超时时，异常恢复场景可用断网验证基础恢复，其他状态码路径标记覆盖缺口。
- 浏览器不支持目标断点模拟时，使用可调整窗口尺寸验证；仍无法覆盖极窄视口时明确标记 SKIP。

审批配置及审批/确认弹窗的统一字号、控件尺寸与间距复测，沿用 [AC-STYLE-01](../approval/approval_configuration.md#ac-style-01-审批页面产品风格一致性)；只打开检查，不提交审批或执行。
