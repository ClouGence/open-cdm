# Approval configuration

## Purpose

验证多个内置审批引擎、团队管理、审批环节拖动和环境绑定；防止新流程依赖资源授权、旧审批被覆盖，以及进行中工单被配置变更影响。

## Scope

- 页面：审批配置的审批引擎、团队 Tab，新增内置引擎、审批环节编辑，环境工单配置。
- 接口：`approval/configuration/query`、`saveEngine`、`saveTeams`、`deleteEngine`、环境绑定、模板列表。
- 工单操作复用 `tests/frontend/ticket/ticket_detail.md`；本文补充自定义审批环节场景。
- 不覆盖真实第三方平台的授权及回调联调。

## Preconditions

- 本地后端已运行且完成 `V202610260001__custom_approval_engine` 迁移；前端使用开发服务输出的 Local URL。
- @Browser 已登录具有配置读写权限、工单申请/查看权限的测试账号。
- 多人场景准备具备审批角色的 A、B，具备执行角色的 C，以及具有资源授权但未配置进引擎的 D。
- 使用已确认可写的隔离测试环境与数据库。SQL 使用 `SELECT 1;`，不得修改共享数据源或生产环境绑定。

## Test Data

- 引擎、团队和工单名称使用 `codex_approval_<唯一标识>` 前缀。
- 团队 T 的成员为 A、B；引擎 E 的第一个环节为 T、N=1，第二个环节为 A；确认环节指定 C。
- 另建引擎 F，验证每个引擎各有一套独立流程。
- 名称上限 128 字符、说明上限 200 字符；团队至少一名成员、至少一个审批环节、团队阈值为正整数且不超过有效审批成员数。配置 JSON UTF-8 编码上限为 60000 字节。

## Suites

### AC-SMOKE-01 入口与页面结构

- 契约复查：审批类型按后端 `Internal` 枚举识别，审批提供者配置只读取 `configValue`；已有第三方配置的关键信息和非密码字段回显正确，密码字段保持留空保留原值。编辑已有内置流程时按后端返回的执行方式显示，新增流程默认手动执行；请求不再携带没有编辑入口的流程描述字段，团队自身的描述仍可编辑。
- 跨页面一致性：审批配置列表、新增类型卡片、环境的 SQL/变更/权限工单配置、工单详情中的内置审批均使用 `logo-clouddm-mark.svg`，不出现旧彩色“内置”图标；提供者中文名称统一为“内置审批”，英文为 Internal approval。具体引擎名称和模板名称按用户配置显示，不替换为提供者名称。环境配置的类型名称直接使用后端国际化结果，刷新及重新打开弹窗后保持一致。
- 优先级/目的：P0，避免入口偏离当前产品结构。
- 初始状态：主页；使用配置读写账号。
- 操作：从导航进入“审批配置”；检查提供者列并刷新；切换“审批引擎”和“团队”；点击新增团队。
- 预期：两个标准 Tab；提供者列中每个内置引擎均显示“内置审批”（英文 Internal approval），名称前显示 20px CloudDM SVG 图标，与第三方提供者图标尺寸及间距一致，刷新后仍显示；审批列表不显示状态列或启用开关；内置及第三方审批保存配置后即可使用，不受遗留启用字段影响；第三方仍要求凭证完整且插件运行正常；启动与保存审批配置不进行鉴权、不建立第三方事件长连接；钉钉、飞书和企业微信配置页提供测试连接按钮，点击时仅校验当前表单凭证，不保存、不启用服务、不启动长连接；编辑时密码留空使用已保存凭证。失败显示错误并结束 loading，不产生后台连接重试；实际创建第三方审批实例时才建立事件连接。测试连接成功不代表回调和所有审批权限均可用；团队在居中弹窗中编辑，底部取消/保存按钮组水平居中；无侧栏表单；列表加载结束，无新的相关 Console 错误。
- 恢复：取消弹窗。

### AC-PLUGIN-LOAD-01 本地部署包含第三方 SDK

- 风险/目的：P0，防止 `local` 用普通 JAR 覆盖带依赖的插件包，导致审批提供者无法加载。
- 初始状态：本地测试服务已通过 Pika Control 停止；不需要真实第三方应用。
- 操作：运行钉钉、飞书和企业微信插件的 `local` 任务；核对运行目录中的包包含 SDK，并再次运行同一任务。重启后打开审批配置新增页，检查三个提供者图标和类型入口，查看当前启动日志与浏览器 Console。
- 预期：两次部署都包含所需依赖：企业微信 `ContentDataValue`、钉钉 `DingTalkClient`、飞书 SDK `OkHttpClient`；不再出现插件加载失败、`ClassNotFoundException` 或 `NoClassDefFoundError`。三个提供者图标正常加载；已配置的提供者按现有规则只能编辑，不能重复新增。打开页面不发起第三方鉴权，也不建立事件连接。插件加载成功不能替代真实应用鉴权及回调验证。
- 清理：取消未提交表单，不创建第三方配置；关闭临时测试标签。

### AC-CONNECTION-01 显式连接测试与失败恢复

- 风险/目的：P0，确认启动、展示和取消配置不自动鉴权，手动测试失败可恢复。
- 初始状态：管理员打开审批配置；没有可用第三方应用时只检查按钮及必填校验，跳过联网测试和回调联调。
- 数据：钉钉使用经确认无效的测试配置；飞书和企业微信在未提交表单中填写明显无效的测试占位凭据，不能读取或覆盖现有密钥。
- @Browser 操作：检查三种类型均有测试连接按钮；空表单点击验证必填提示；补齐无效测试输入后点击，观察 loading 和错误，再取消表单。列表中对独立测试配置点击测试连接；检查其他行不被一起禁用。退出页面后检查没有后台重试。
- 预期：缺字段时仅本地校验；调用失败有明确错误且恢复按钮；不保存表单、不启动事件长连接；列表仅本次请求行进入 loading；其他提供者仍可测试，同一提供者重复点击不会重复请求，成功和失败都会恢复该行按钮。重新启动服务后没有第三方自动鉴权或连接失败重试。真实连接成功、发起审批及回调必须依赖可用应用，不能用无效占位数据替代。
- 清理：取消未提交表单；不修改原第三方配置。

### AC-MAIN-01 团队和多个引擎

### AC-FORM-01 各类型表单样式

- 优先级/目的：P1，避免内置与第三方类型、标题和页脚风格不一致。
- 初始状态：审批配置新增页；配置读写账号，第三方类型尚未配置。

- 安全规则标签不显示必填星号，未选择规则时仍需阻止提交。
- 恢复：关闭检查用弹窗，取消表单，保持全部原有业务数据。

### AC-MAIN-02 横向拖动与字段清理

- 优先级/目的：P0，验证排序与参与者切换。
- 初始状态：E 配置页，至少两个不同参与者的环节。
- 操作：检查画布顶部的添加、删除按钮，包括鼠标悬停、键盘聚焦和按下删除按钮时的颜色；通过顶部添加按钮在当前选中环节后插入新环节，选中其他环节后点击顶部删除；仅剩一个环节时检查删除禁用。检查右上角缩小、百分比、放大和适应画布，验证 50%/150% 边界；通过卡片加号添加多环节，缩放后拖动换序，再适应画布；在 50%、100%、150% 下检查相邻卡片间的连接线，再增删环节并检查末环节。切换团队和指定一人；在右侧确认环节选择团队或个人，切换选中的审批环节、添加和拖动环节后检查确认配置不变；保存后重入。
- 预期：顶部与卡片内的添加、删除操作一致，作用于当前选中环节，至少保留一个环节；顶部删除按钮可用时的悬停、聚焦和按下态使用与 CI/CD 一致的红色文字、边框及浅红背景，不出现绿色；仅剩一个环节时保持禁用样式且不能删除；只读账号不显示顶部操作按钮，但可使用缩放控件查看流程；缩放按 10% 调整、边界按钮禁用，不改变环节配置和顺序，适应画布在 50%～100% 内自动缩小并居中，仍超出最小缩放范围时可滚动查看。卡片水平排列、序号更新、顺序持久化；连接线在各缩放比例下从前一卡片右边缘连续接到后一卡片左边缘，两端没有留白，垂直位置与卡片中心对齐；增删和重排后连接线跟随相邻卡片，最后一个及单个环节没有向外伸出的连接线；卡片复用 CI/CD 节点的 264×128 尺寸、8px 圆角、字体、内边距与操作图标，画布浅底居中；右侧配置区依次显示“审批环节”和“确认环节”，确认配置绑定整个引擎，切换、添加、删除或重排审批环节不改变确认人员；确认类型切换和团队/个人选择仍可操作，保存重入保持配置；窄屏时两块表单一起堆叠在画布下方，无横向溢出；审批配置标题固定为“审批环节”，不显示“环节 1”等序号；无自定义环节名称、复制、移动箭头、全部人通过；团队卡片名称后显示人数，个人卡片只有姓名和底部规则；切换类型后隐藏字段不参与请求。
- 恢复：恢复测试流程或删除 E。

### AC-MAIN-03 多人明细与通过人数阈值

- 优先级/目的：P0，验证一个团队内每个人的结果、时间、意见独立保存，只有达到配置票数才推进。
- 初始状态：隔离演示环境；管理员和专用审批人 A/B，A/B 仅有审批与查看角色，无数据源资源授权；通过 @Browser 的独立登录会话操作，不读取认证数据。
- 测试数据：新建唯一标识团队，包含管理员、A、B 三人，第一环节要求两票通过；第二环节另选管理员所在团队，需一票；确认环节也使用有效团队。临时绑定隔离环境的 SQL 工单并记录原绑定，正常创建唯一标题的 `SELECT 1;` 工单。
- 操作：展开全部环节，核对第一环节三人的待审批行和第二环节未开始。管理员在自己行提交第一票及可识别意见，刷新后核对 1/2 和下一环节；管理员已投票后检查审批按钮。A 从独立会话的待办进入同一工单，检查只有自己的待审批行可操作，填写另一条意见并同意。管理员刷新后逐行核对全部记录及下一环节，离开并重新进入，再检查 1440×900、1024×768、390×844 下的表格。
- 预期：第一票只更新管理员行的结果、真实提交时间和意见，A/B 仍待审批且时间、意见为“-”；票数 1/2，第一环节仍等待审批、第二环节未开始，管理员不能重复投第二票。A 投票后第一环节为已通过、2/2，A 的时间和意见与管理员独立，原管理员记录不变；未投票 B 显示已关闭，审批时间和意见仍为“-”。只有此时第二环节进入等待审批，管理员必须在新环节自己的行重新审批，不能沿用前一票。A 在下一环节无审批按钮；刷新、恢复原环境绑定和停用已结束任务的测试成员后，历史明细仍保持一致。三种宽度下全部人员均可查看，长意见折行，表格内部横向滚动，页面不溢出。本场景为顺序投票，不替代 AC-CONCURRENCY-02 的真实并发验证。
- 恢复：恢复环境原绑定，停用本次专用账号，不修改共享账号权限。工单停留下一审批环节供核对，不执行 SQL；保留被冻结流程引用的团队、引擎和审计，不能删除仍被引用的配置。

### AC-MAIN-04 同一团队一人同意、另一人拒绝

### AC-PERMISSION-02 跨账号、跨租户与资源授权对照

### AC-CONCURRENCY-02 真实并发投票与环节推进

- 优先级/目的：P0，防止重复计票、跳环节、迟到拒绝反转及终态复活。
- 初始状态：隔离测试库中准备两环节工单，第一环节为 A/B 团队、N=2，第二环节为 A；另准备 N=1 的同团队工单。通过真实登录接口建立每个账号的独立 HTTP 会话，不读取浏览器认证数据。
- 操作：在独立数据库会话仅锁定本次测试工单行；同时发起多条 HTTP 请求，通过 `performance_schema.data_lock_waits` 的不同请求线程确认至少两个服务端事务等待该行，然后释放锁。分别执行 A 的 12 条重复同意、A/B 两票并发、最后环节 8 条重复同意；重放旧环节请求，提交同一任务相反动作；对 N=1 工单重复执行 A 同意与 B 拒绝竞争。再让最终审批与申请人取消竞争。每次同时检查响应、数据库任务行、当前环节和 @Browser 刷新结果。
- 预期：同一人只计一票且首次意见不被覆盖；两人达标只推进一次；相邻同人环节仍须独立投票；最后环节只进入一个确认阶段；旧环节重试不影响下一环节。达到阈值或有效拒绝中先提交者生效，后到冲突操作被拒绝；拒绝或取消后无 PENDING/WAITING 任务，迟到请求不能恢复工单。任务 `(process_activity_id, approver_uid)` 没有重复行。
- 恢复：无论断言是否成功，立即释放数据库测试锁；取消本次未完成工单。不得锁共享或生产工单，不得仅用顺序请求或 Mock 测试宣称真实并发通过。

### AC-CONCURRENCY-03 确认执行幂等

- 优先级/目的：P0，避免重复确认生成或启动多个执行任务。

- 预期：仅配置名单内且保留执行角色的 C 可确认；同请求号只生成并启动一个执行作业，实际执行人记录为 C，SQL 执行一次并完成；原请求重试不重新执行，改内容或新请求号不能再次执行终态工单；作业和任务必须归属同一工单。
- 恢复：保留完成记录与任务日志，取消未完成测试工单，不删除审计历史。

### AC-PERMISSION-03 在途名单冻结与角色失效

### AC-RECOVERY-01 服务重启与执行准备恢复

### AC-RECOVERY-02 定时执行跨重启与到期补偿

- 风险/目的：P0，防止任务提前执行、停机期间到期后丢失，或者重启重复创建和执行作业。
- 初始状态：专用环境、独立数据库和两环节团队审批配置；审批通过后由配置中的执行人确认。分别准备 SQL 工单和从内置发布流触发的变更工单。
- 测试数据：独立库中创建带主键和唯一场景名的检查表，每个工单仅插入自己的标识；不使用共享业务表。记录本次工单、作业、任务和数据库行的标识。
- @Browser 操作：完成两个审批环节，核对每人的结果、时间和不同意见；选择定时执行并输入未来的准确时刻，选择事务模式后确认。第一条任务在到期前通过 Pika Control 重启后端；第二条在到期前停止后端，保持停机跨过计划时刻后再启动。每次启动均核对新执行实例、健康检查和插件就绪；浏览器刷新并重新进入工单。
- 预期：确认后计划时刻持久化，未到时没有实际写入；提前重启不提前执行；停机期间没有写入，到期后启动能够补偿执行。每张工单仅有一个作业和相应任务，最终完成，执行次数为 1，检查表每个场景仅一行。变更工单完成后关联发布流变更也完成，触发入口恢复可用；调度日志属于当前作业。再重启和刷新已完成工单，记录和执行次数不变。
- 清理：所有任务到达终态后删除本轮独立工单、发布流、配置引用及专用数据库，不改变共享环境绑定。

### AC-RECOVERY-03 单机执行中断后的暂停与人工恢复

- 风险/目的：P0，防止嵌入式 worker 重启后遗留没有执行线程的“执行中”任务，或恢复时重放已完成 SQL。
- 初始状态：单机 DmAloneLauncher；独立测试库；正常完成团队审批并进入人工确认的 SQL 工单。
- 测试数据：关闭事务，依次执行插入唯一检查点、`SELECT SLEEP(35);`、插入另一个唯一检查点；写入仅限专用测试表。
- @Browser 操作：确认立即执行；通过只读数据库观察第一条任务完成、第二条任务正在执行，随后通过 Pika Control 停止当前精确实例并重新启动。等待 worker 就绪，刷新工单；核对暂停状态、警告和恢复入口。点击恢复并确认，等待剩余语句完成；刷新并再次重启后查看终态。
- 预期：重启恢复处理发生在嵌入式 worker 启动之前，原作业进入暂停且标记异常中断，不会自动重放可能已产生副作用的 SQL。步骤详情明确显示“已暂停”，不显示“-”；原审批意见不变。人工恢复后仅重试未完成任务，第一条已完成任务执行次数仍为 1，两个检查点各只有一行，最终工单和作业完成。已完成工单重启后不新增任务、不重新执行。
- 清理：任务结束后删除本轮测试记录和专用数据库；停止自己启动的前端开发服务。

### AC-LIFECYCLE-02 终态工单刷新与重新进入

- 优先级/目的：P0，确认后台调度修复后，完成和取消记录不会在页面刷新时变为执行失败或重新出现执行入口。

- 操作：分别从列表打开两张工单，等待加载结束；检查环节、执行结果和可用操作；刷新详情，再返回全部列表重新进入。后端服务重启后重复上述检查。
- 预期：完成工单仍显示完成，执行结果保持成功且执行次数不增加；取消工单仍显示取消，未处理环节保持关闭；均无新的确认或执行入口，无相关 Console 错误。此场景仅验证页面持久化展示，迟到调度、条件抢占和并发取消必须另用后端受控测试验证，不能以页面刷新替代。
- 恢复：保留终态测试记录，不修改历史状态或重新执行 SQL。

### AC-LIST-SCOPE-01 工单列表权限与分页

- 优先级/目的：P0，简化列表查询后，确保自定义工单的全部列表、待办、总数和分页保持正确。
- 初始状态：同租户已有管理员、参与审批账号、仅执行账号及非参与账号；至少两个不同内置流程及一条旧内置或第三方工单；不修改共享授权。
- 数据准备：通过正常流程创建分别由审批人 A、确认人 C 处理的测试工单，包含未来环节、已处理环节和其他流程工单；数据足够覆盖两个分页时执行分页检查。已有稳定记录可直接复用，不依赖固定工单 ID。
- 操作：分别用管理员、A、C 查看“全部”和“待办”，记录工单号及总数；切换页码、查询无匹配结果，再清空筛选。A 在当前环节未激活、激活及投票后分别查看待办；C 在待审批和待确认时分别查看。切到无关流程的工单号检查列表及详情访问；刷新、重入并核对。变更实现的回归可在同一批只读数据上对比变更前后的列表工单号、顺序、总数及第二页。
- 预期：管理员和工单申请人的既有可见范围不变；有效审批人可在全部列表查看其历史或未来参与记录，待办仅出现当前仍待本人处理的环节；有效确认人能查看授权流程，只有待确认时进入待办。非参与账号不能因全局资源权限看见无关自定义工单。旧流程仍按既有人员关系显示。权限过滤在数据库分页之前生效，总数等于符合权限和筛选条件的工单数；没有空洞页、重复记录、跨页丢失或越权后在前端隐藏的记录。空参与 ID 集合不会生成空 IN 条件或放开自定义工单范围；异常执行快照不授予额外可见性。旧流程人员关系、自定义审批参与关系与执行快照均通过简单查询批量读取，在 Java 合并待办工单 ID 并去重；分页 SQL 只按租户、工单 ID 和页面筛选条件过滤，不使用 JOIN、GROUP BY、相关 EXISTS 子查询或 JSON 权限运算。
- 恢复：清空筛选、恢复原列表页码和账号页面；本场景只读，不创建新授权、不审批或执行已有用户工单。无对应账号或分页数据时报告覆盖缺口，不伪造权限结果。

### AC-EXECUTION-MODE-01 手动与 CloudDM 自动执行

- 优先级/目的：P0，确认执行方式持久化、按工单快照生效，自动模式仅在全部环节通过后执行且保留租户隔离。
- 初始状态：独立本地测试环境、可连接的测试实例和 `SELECT 1;`；新建含两个审批团队环节的内置引擎。不得改变共享环境或现有用户测试工单。
- 数据准备：使用 `codex_exec_mode_<唯一标识>` 命名专用引擎、环境和实例；环境的 SQL 工单绑定专用引擎。无需创建系统登录账号或调整共享用户权限。
- 操作：在确认环节核对“审批方式”“执行方式”及手动模式的“确认人”均有必填星号；配置审批团队后，在确认团队或个人留空时尝试添加或保存，核对阻止提交且配置仍保留；核对“自动执行”选项右侧的说明图标，分别在手动和自动模式下悬停图标后查看说明并移出关闭；保存、重新打开、刷新。正常提交 SQL 工单，同意第一环节，等待至少两个自动刷新周期后检查未执行；再同意最后环节，不点击任何执行按钮，等待系统完成。展开执行任务核对 SQL、状态和执行次数；重复刷新和重新进入。另建相同工单，第一环节同意、第二环节拒绝。随后把专用引擎改为“手动执行”，选择有效团队或个人，保存重入；新建手动对照工单并通过全部环节，核对停在确认，点击步骤详情底部执行按钮打开原弹窗后取消。再次查看原自动工单，确认修改引擎未改变历史快照。分别在 1440×900、1024×768、390×844 下检查执行方式字段和详情按钮。
- 预期：新建及既有未配置执行方式的流程默认手动；手动模式必须选择有效确认团队或个人。手动模式的“团队 / 指定一人”上方显示“确认人”，与“执行方式”分开；自动模式不要求选择真人，配置面板不再另列 CloudDM 图标或文字；说明图标与“自动执行”选项的间隔为 4px，单选项末尾没有额外右外边距，点击或悬停图标不切换执行方式，说明正文默认不占据面板空间，悬停后才展示完整内容，移出后隐藏；保存的 executionMode 为 AUTO、executionAssignment 为空；手动保存为 MANUAL。自动模式第一环节通过不创建执行任务；全部环节通过后由调度器完成确认并执行，确认与执行处理人显示 CloudDM，单条 SQL 执行一次，刷新不重复启动；拒绝后确认和执行均关闭，无执行任务。手动模式全部通过后仍待确认，执行按钮仅出现在确认步骤详情底部且原弹窗取消不创建作业。已有工单沿用创建时的模式，后续更改模板不修改在途或历史工单。自动模式的系统调度使用工单所属租户身份及目标数据源连接配置，不允许客户端确认请求冒充系统、指定其他租户执行身份，或跳过未完成的审批；权限工单仍按已有授权流程处理，不产生 SQL 作业。
- 异常恢复：仅在隔离环境使用可复现的任务准备失败或执行失败条件，确认失败进入明确终态而非无限自动重试；系统重启及任务队列繁忙沿用持久化执行尝试恢复，不能重复启动同一作业。没有可安全构造的故障时报告该项未执行，不以成功路径替代。
- 恢复：保留必要的完成/拒绝证据供复查；取消未提交弹窗，关闭未执行的本次手动工单。仅清理本流程创建且不再引用的专用配置；不执行或关闭用户原有测试工单，不修改数据库内容。

### AC-PERMISSION-04 直接 HTTP 调用不能绕过角色权限

- 优先级/目的：P0，验证服务端授权，不能用按钮隐藏代替接口拦截。
- 初始状态：隔离本地服务；管理员、只读角色（仅对应 READ 权限）、仅 `DM_QUERY_CONSOLE` 的无管理权限账号，以及未登录会话。使用正常登录接口建立独立 HTTP 会话，不提取浏览器 Cookie、存储或已有用户凭据；请求使用当前公开的 SM2 登录公钥加密测试账号密码。不得输出密码、Cookie 或令牌。
- 受限接口：审批配置 `saveEngine/saveTeams/deleteEngine/testConnection`；环境 `dsenv/add/update/delete/listSpec`、`envparam/bindEnvParam/unbindEnvParam`；审批模板 `refreshTemplates/addTemplate/removeTemplate`；安全规则 `specUpdateInfo/specConfig/specDelete/specCreate/specSaveRule/specSaveRules/ruleSave/ruleDelete`、范围 `specSaveRange/specDeleteRange`；账户 `addSubAccount/updateSubAccount/deleteSubAccount/updateUserRole`；资源授权 `modifyUserAuth/batchModifyUserAuth`；通用配置 `upsertUserConfigs`；工单 `approval/confirm/retryAutoExecJob/stopAutoExecJob/skipAutoExecTask/continueAutoExecTask/endAutoExecJob`。
- 操作：分别直接 POST 上述接口。先用空对象确认权限校验先于参数处理；再填写格式有效的字段，资源 ID 使用不存在的测试标识，附加伪造的 `uid/puid/roleId/isMaintainer`。检查 HTTP 状态与业务 success。只读账号对 `configuration/query`、`specList`、`listSubAccounts`、`listRules`、`listUserAuthRes`、`listTemplates`、`approvalType` 发起合法查询；后两者不要求额外的数据源权限。授权查询传 `targetUid` 与 `authKind=DataSource`。
- 预期：受限角色直接操作返回项目统一的 406 权限拒绝，未登录返回 401；不进入写入、第三方测试或 SQL 执行流程。伪造请求体身份不能覆盖服务端登录身份。合法只读查询返回 200 且 `success=true`；无权限账号相同查询被拒绝。拒绝响应不得因参数错误被误判通过，不把 200 且 `success=false` 当作正常查询成功。
- 权限边界：环境绑定、解绑、可配置规则选择和模板变更均为 `RDP_ENV_MANAGE`；模板和提供者列表为 `RDP_ENV_READ`；不接受仅有 `DM_DS_MANAGE/DM_DS_READ` 的账号替代环境权限。引擎、团队保存和测试连接为 `RDP_PRI_USER_KV_CONF_W`。审批和执行仍检查工单归属、当前环节及登录用户资格。
- 合法对照：管理员通过 @Browser 新建无实例绑定的空环境，保存该环境的 SQL 审批模板，配置已有规则后解绑；刷新确认结果。只操作本轮创建的环境，不修改共享绑定。
- 清理：删除临时空环境，停用测试账号，退出独立 HTTP 会话并清除临时凭据文件；不提交或保留 Cookie、令牌和原始响应中的敏感数据。

## Cleanup

恢复环境原有的三类工单绑定；删除本流程创建且无引用的引擎和团队。恢复临时变更的测试账号角色。不删除审批历史、任务审计记录、迁移记录或共享数据库数据。

## Skip Conditions

缺少对应角色账号、确认可写的测试数据源、@Browser 登录或可控的失败注入能力时，相关权限、并发或恢复场景不可标记通过。CLI 编译与单元测试只能作为代码层证据，不替代浏览器业务验证；工具不支持调整视口时明确记录布局覆盖缺口。
